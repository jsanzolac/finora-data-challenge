01Summary

The system has two read paths over one gold layer. A precomputed path serves every page load in milliseconds. A governed on-demand path answers new questions with Athena, without leaving the agreed use cases.

  1. Two read paths. Dashboard snapshots and the Claude briefing are built once per gold refresh. Athena runs only for questions the snapshots cannot answer.
  2. The semantic layer is the contract. Every question becomes a structured query spec, checked against a metric catalog and compiled to SQL by code. No model writes SQL.
  3. Claude on Bedrock does the analysis. It writes the briefing on each refresh and turns spoken questions into query specs. Every number it states comes from SQL results.
  4. The voice agent pulls its own data. At session start, an ElevenLabs webhook tool calls the analytics API with the user's OAuth token. The briefing and the catalog never pass through the browser.
  5. Access is enforced in the API, not the prompt. A JWT authorizer checks scopes, and the compiler adds row-level filters from the token's claims to every query.

02Goals and scope

Users get a dashboard of fixed base analyses, plus a voice agent that explains them and answers follow-up questions. A base use case is one agreed analysis, such as sales performance by channel and region. Each one maps to a set of gold views and catalog metrics.

RequirementHow the design meets it
Dashboard loads fast and cheaplyPrecomputed snapshots per view and data partition; no Athena on page load
Agent knows the latest numbers at session startBriefing built on each refresh, fetched by the agent's get_briefing tool
Key analysis facts written by ClaudeBedrock call in the refresh pipeline, checked against the KPI table
Users can ask for new measures or cutsrun_analysis tool → query spec → semantic layer → Athena
New analysis stays within the base use casesCatalog defines allowed views, metrics, dimensions and derived-metric operations
Semantic context and data stay protectedOAuth token with scopes, server-to-server tool calls, row-level filters

Out of scope for this version: writing to the lake from the dashboard, free-form SQL, and questions that need data outside gold.

04Data lake

Each layer has one job, its own S3 prefix or bucket, and its own Glue Data Catalog database.

LayerWhat it holdsFormatWritten by
Landing (staging)Files exactly as sources deliver themAs delivered (CSV, JSON, Excel)Source systems, SFTP, uploads
BronzeImmutable raw copy, plus ingestion metadata (source file, load time, hash)Parquet, partitioned by ingest dateIngest job
SilverCleaned, typed, deduplicated, with conformed keys and quality checksIceberg tablesGlue Spark jobs or dbt on Athena
GoldBusiness marts per use case: facts, dimensions, aggregatesIceberg tables and viewsdbt on Athena or Glue

How a file moves through the layers

  1. A file lands in s3://<lake>-landing/source=<system>/ingest_date=YYYY-MM-DD/. S3 sends an Object Created event to EventBridge.
  2. EventBridge starts the ingest state machine in Step Functions. It writes the file to bronze as Parquet with its metadata, then tags the landing object as processed. S3 has no real move: it is a copy, then a delete or expiry.
  3. A lifecycle rule keeps landing files for a set number of days, so any load can be replayed.
  4. Bronze to silver applies types, deduplication and data quality rules (Glue Data Quality or dbt tests). Rows that fail go to a quarantine table instead of being dropped silently.
  5. Silver to gold builds the marts. When it finishes, Step Functions publishes a gold.refreshed event with the refresh version and the tables that changed.

Rules for gold

  • Gold column names and meanings are a contract. The semantic layer points at gold views, so a renamed column ships with its catalog change in the same release.
  • Partition gold facts by date and keep files compacted. Athena bills by data scanned, so this sets the cost of every on-demand question.
  • Use Iceberg so late or corrected records can be merged, and earlier versions queried.
  • Restrict the analytics role to gold with IAM policies on the gold S3 prefix and Glue databases. Lake Formation also works, but Athena cannot reuse query results on tables registered with it.

05Refresh pipeline: snapshots and the Claude briefing

The gold.refreshed event starts one state machine that prepares everything the dashboard and the agent read. Nothing here runs when a user opens the page: the data only changes on refresh, so once per refresh is enough.

  1. Compute KPIs. Run the base dashboard queries from the catalog in Athena, once per view and per data partition a role can see (for example, per region or per client).
  2. Compute changes in code. Period-over-period change, change against the trailing average, and simple anomaly flags. These numbers come from code, not from the model.
  3. Write snapshots. Save one JSON file per view and partition to s3://<serving>/v=<refresh_version>/<partition>/<view>.json.
  4. Ask Claude for the briefing. Send Claude on Bedrock the KPI table, the changes and the metric definitions. Ask for 5 to 8 key facts through a tool-use JSON schema, so the output is structured.
  5. Check the briefing. Every number in the text must match a value in the input, within rounding. If one doesn't, regenerate once, then fall back to a template briefing built from the changes alone.
  6. Publish. Write briefing.json next to the snapshots, then switch the latest pointer (one DynamoDB item per partition) to the new version. The dashboard and the agent move to the new data at the same moment.

The briefing also carries short definitions of the metrics it mentions, so the agent never needs the full catalog.

Briefing format, with example values:

{
  "as_of": "2026-11-15T06:00",
  "partition": "region=Andina",
  "facts": [
    {
      "metric_id": "revenue",
      "label": "Revenue",
      "period": "2026-10",
      "value": 1250000,
      "unit": "USD",
      "change_pct": -4.2,
      "compared_to": "2026-09",
      "statement": "October revenue fell 4.2% from September, driven by the online channel.",
      "drivers": [{ "dimension": "channel", "value": "online", "change_pct": -11.0 }]
    }
  ],
  "definitions": {
    "revenue": "Net order value after returns, before tax."
  },
  "caveats": ["Returns for the last week of October are still being processed."]
}

06Semantic layer

The semantic layer is what lets users ask for new analysis without leaving the base use cases. A question can combine catalog parts in new ways, but it can never reach anything outside the catalog.

It has three parts:

  1. Metric catalog: YAML files in the repo, versioned and reviewed like code.
  2. Query spec: a small JSON format that every question is translated into.
  3. Compiler: code that validates a spec and turns it into one Athena SQL query.

Metric catalog

For each base use case, the catalog lists:

  • Sources: the gold views it may read, and how they join.
  • Dimensions: name, column, type, allowed values and synonyms ("canal" means channel).
  • Measures: an aggregation over a column, such as sum(net_amount).
  • Metrics: named business metrics built from measures, each with a plain-language description.
  • Time: the time column, allowed grains (day, week, month) and the longest allowed range.
  • Access: the scope a metric requires, and which token claims become row filters.

Example for an illustrative retail use case:

use_case: sales_performance
sources:
  orders: { view: gold.v_orders, time: order_date }
  stores: { view: gold.v_stores, join: "orders.store_id = stores.store_id" }
dimensions:
  channel:  { column: orders.channel, values: [online, store], synonyms: [canal] }
  region:   { column: stores.region, synonyms: [zona] }
  category: { column: orders.category }
measures:
  net_amount:  { expr: "sum(orders.net_amount)" }
  order_count: { expr: "count(distinct orders.order_id)" }
metrics:
  revenue: { measure: net_amount, description: "Net order value after returns, before tax" }
  orders:  { measure: order_count, description: "Number of distinct orders" }
  aov:     { ratio: [revenue, orders], description: "Average order value" }
time: { grains: [day, week, month], max_range_days: 730 }
access:
  scope: analytics/sales.read
  row_filters: { region: claims.regions }

Query spec

Every question, spoken or typed, becomes this shape before anything runs. This one asks for the online share of revenue, by week, over the last 8 weeks:

{
  "use_case": "sales_performance",
  "metrics": [],
  "derived": [
    { "name": "online_share", "op": "share", "of": "revenue", "where": { "channel": "online" } }
  ],
  "dimensions": [],
  "filters": [],
  "time": { "range": "last_8_weeks", "grain": "week" },
  "compare": null,
  "limit": 50
}

What counts as in scope

Request typeExampleResult
Catalog metric, new cut"Revenue by region last month"In scope: runs directly
New filter or time window"Electronics only, last 8 weeks"In scope: runs directly
Derived metric from catalog parts"Online share of revenue by week"Extension: runs, logged as ad hoc
Needs data that is not in the catalog"Customer churn this quarter" (no customer data in gold)Out of scope: agent explains, request is logged
Use case the user has no scope for"Payroll costs by store"Refused by access rules

A metric can be created at question time only through these operations, and only from catalog metrics and dimensions:

OperationMeaningExample
ratio(a, b)a divided by bRevenue per order
share(a, where)The part of a that meets a condition, over all of aOnline share of revenue
growth(a, period)Change of a against an earlier periodRevenue vs. the same month last year
rolling(a, window)Moving sum or average4-week rolling orders
filtered(a, where)a under a fixed conditionRevenue from electronics only
top_n(a, by, n)RankingTop 5 categories by revenue

Compiler rules

  • Reject any spec that names something outside the catalog, or an operation outside the list above.
  • Build the SQL with a library (sqlglot, Athena/Trino dialect), never by pasting model text into a template.
  • Always add the row filters from the token's claims and a time filter on the partition column. The spec cannot remove them.
  • Cap the row count and the time range.
  • Output exactly one SELECT over gold views.

Who writes the spec

Claude on Bedrock writes it, inside the analytics API. The voice agent only passes the user's words. The API sends Claude the question, the matching catalog entries and the previous result, and Claude returns a spec through a tool-use schema. This keeps the catalog out of ElevenLabs and puts all the semantic reasoning in one place you control.

07Analytics API

One API Gateway HTTP API serves both the dashboard and the voice agent. Every route requires a valid JWT and the scope listed below.

RouteCalled byWhat it doesScopeTarget latency
GET /dashboard/{view}Next.js serverReturns the latest snapshot for the caller's partitionanalytics/dashboard.readUnder 200 ms
GET /agent/briefingElevenLabs webhook toolReturns briefing.json for the caller's partitionanalytics/briefing.readUnder 200 ms
POST /analysisElevenLabs webhook tool, dashboard ask boxQuestion → spec → SQL → Athena, then result and summaryanalytics/query.run3 to 15 s
GET /results/{id}Browser, after render_chartReturns the rows and chart spec of a finished analysisanalytics/query.runUnder 200 ms

What POST /analysis does

  1. Read the user's claims from the validated token: user, roles, regions.
  2. Ask Claude on Bedrock to turn the question into a query spec, or to mark it out of scope with a reason.
  3. Validate and compile the spec with the semantic layer rules.
  4. Run the SQL in Athena: StartQueryExecution, then poll until it finishes.
  5. Store the rows under a result_id (S3 or DynamoDB, with an expiry).
  6. Ask Claude for a two-sentence spoken summary built only from the rows, and check its numbers against them.
  7. Return {status, result_id, summary, chart_hint, scope_class}. The rows are not sent to the agent.

Athena settings

  • Use a dedicated workgroup with a per-query data-scanned limit, so a bad query fails instead of scanning the whole lake.
  • Turn on query result reuse. Athena reuses a matching result from the same workgroup if it is younger than the maximum age you set: 60 minutes by default, up to 7 days. It does not work on tables registered with Lake Formation, which is why gold access uses IAM.
  • Also cache in your own code: a spec with the same normalized hash, partition and refresh version returns the stored result without calling Athena.

Timeouts

An HTTP API stops waiting for its integration after 30 seconds at most, and this cannot be raised. Keep the Lambda's wait for Athena under about 20 seconds. If the query is still running, return status: "running" with the result_id. The agent then says the chart will appear on screen, and the browser polls GET /results/{id}.

Athena keeps running the query after the Lambda returns. GET /results/{id} checks its status, then stores the rows and summary once it finishes.

08Frontend: Next.js and D3

The site draws the base dashboard from snapshots and hosts the voice session. It only ever holds data the logged-in user is allowed to see.

  • Hosting: AWS Amplify Hosting, or a container on ECS Fargate behind CloudFront.
  • Login: OAuth 2.0 / OIDC with Cognito or your existing identity provider, through Auth.js in Next.js. The access token carries the user, roles, partitions and scopes.
  • Data loading: server components call GET /dashboard/{view} with the user's token and pass the JSON to client components.
  • Charts: D3 inside React client components. One component per chart type (line, bar, table), driven by a chart spec {type, x, y, series, unit}. Base charts and agent-requested charts use the same components.
  • Agent session route: /api/agent-session runs on the server. It gets an ElevenLabs signed URL using the ElevenLabs API key from Secrets Manager, and returns it with the agent token (see Security).
  • Voice UI: useConversation from @elevenlabs/react, started with the signed URL, secret__access_token as the only dynamic variable, and the client tools below.
  • Ask box (optional): a text field that calls POST /analysis, so typed and spoken questions share one path.

Client tools the page registers:

ToolParametersWhat the page does
render_chartresult_idFetches GET /results/{id} with the user's token and draws the chart in the analysis panel
focus_viewview, filtersSwitches the dashboard tab or applies filters to a base view
highlight_metricmetric_idHighlights the KPI card the agent is talking about

The agent only ever passes IDs to the browser. The browser fetches the data itself, with the user's own token.

09Voice agent (ElevenLabs)

The agent handles the conversation: it talks, decides which tool to call, and reads out results. All data and analysis come from your API through its tools.

Configuration

  • Authentication: require signed URLs, so no one can open the agent without going through your server.
  • First message: fixed, for example "Hi, I'm loading today's numbers." It covers the first tool call.
  • Dynamic variables: only secret__access_token. ElevenLabs uses secret variables in tool headers and never sends them to the LLM.
  • Conversation LLM: chosen in the agent settings. If conversation text must stay inside your AWS account, evaluate ElevenLabs' custom model option pointed at Bedrock.
  • Retention: ElevenLabs stores transcripts and tool results. Set retention to the minimum you need; zero retention is an Enterprise option.

Tools

ToolTypeCallPurpose
get_briefingWebhookGET /agent/briefing, header Authorization: Bearer {{secret__access_token}}Latest metrics, definitions and key facts for this user
run_analysisWebhookPOST /analysis with {question, previous_result_id}, same headerNew cut, derived metric or comparison
render_chartClientresult_idDraws the result in the browser
focus_viewClientview, filtersMoves the dashboard to what is being discussed
highlight_metricClientmetric_idPoints at a KPI card while talking about it

Session and question flow

  1. The user clicks the microphone. The browser calls /api/agent-session on the Next.js server.
  2. The server asks ElevenLabs for a signed URL, using the ElevenLabs API key.
  3. ElevenLabs returns the signed URL.
  4. The server returns the signed URL and the user's agent token to the browser.
  5. The browser starts the session with the token as secret__access_token and registers the client tools. The agent says its fixed first message.
  6. The agent calls get_briefing. ElevenLabs calls the API directly, with the token in the Authorization header.
  7. The JWT authorizer validates the token, and the Lambda returns that user's briefing. The agent states the two or three most important facts.
  8. The user asks a new question. The agent calls run_analysis with the user's words.
  9. The API returns the spoken summary and a result_id, not the rows.
  10. The agent reads the summary and calls the client tool render_chart(result_id) in the browser.
  11. The browser calls GET /results/{id} with the user's token.
  12. The API returns the rows and chart spec, and D3 draws the chart.

Core prompt rules

  • Call get_briefing before discussing any number.
  • Never state a number that did not come from a tool result.
  • For any question the briefing cannot answer, call run_analysis with the user's own words.
  • Say a short filler before run_analysis, such as "Let me pull that."
  • When a result has a result_id, call render_chart so the user can see it.
  • If the result is out of scope, say what data is missing and offer the closest analysis that is in scope.
  • If a tool returns 401, ask the user to refresh the page to continue.

10Security and access control

The browser only carries the user's own token. Data moves server to server, or through authorized API calls made with that token.

The token (OAuth ticket)

  • Your identity provider issues it after login. Claims: sub (the user), roles, data partitions (such as regions), scopes, aud (the analytics API) and exp.
  • Use a token dedicated to the agent: read-only scopes, audience limited to the analytics API, and a lifetime a little longer than the longest expected session (for example 30 to 60 minutes).
  • To issue it, use OAuth token exchange if your provider supports it, or a separate app client with short token validity.
  • In Cognito, a version 2 pre-token-generation Lambda trigger adds custom claims and scopes to access tokens. It needs the Cognito Essentials or Plus feature plan.
  • Never give the agent a refresh token or the main session cookie.

Where access is enforced

LayerCheck
API GatewayJWT authorizer: signature, issuer, audience, expiry, and the route's scope
Analytics LambdaMaps claims to row filters; checks each metric's catalog scope
CompilerAdds the row filters to every SQL query; the spec cannot override them
Athena and IAMThe Lambda's role reads gold views only; the workgroup caps data scanned per query
ElevenLabsSigned URLs required; token held as a secret variable, used in headers only, never in the LLM prompt
BrowserGets snapshots and results only through authorized calls with the user's token

Known exposures and how each is handled

  • The token is visible in the browser. It is the user's own short-lived, read-only token. Used outside the agent, it returns only what the user can already see.
  • ElevenLabs holds the token for the session. Post-call webhooks deliver secret variables in their original form. Keep tokens short-lived and send post-call webhooks only to your own endpoint.
  • Transcripts are stored at ElevenLabs. Tools return summaries and IDs, not raw rows. Set retention to the minimum.
  • Prompt injection through a question. The worst case is a bad spec, which the compiler rejects. Model output never becomes SQL directly and cannot remove row filters.
  • The token expires mid-session. Tools get a 401 and the agent asks the user to refresh. The page can also start a new session with a fresh token.

11Worked cases

Four end-to-end flows, using the illustrative retail catalog from the semantic layer section. All numbers are examples.

Case 1: gold refreshes at 06:00

  1. The silver-to-gold job finishes and publishes gold.refreshed with version 2026-11-15T06:00.
  2. The refresh state machine runs the base KPI queries once for each region partition.
  3. Code computes the changes. For Andina: October revenue down 4.2% from September; online channel down 11%.
  4. Claude writes the key facts. The checker confirms that 4.2% and 11% appear in the input table.
  5. Snapshots and briefing.json are written under the new version, then the latest pointer switches.

Result: every page load and every new voice session now sees the 06:00 data, and no Athena query runs at read time.

Case 2: a regional manager opens the dashboard and starts the agent

  1. She logs in. Her token has regions: [Andina] and the scopes dashboard.read, briefing.read and query.run.
  2. Next.js calls GET /dashboard/sales with her token. The Lambda returns the Andina snapshot, and D3 draws the charts.
  3. She clicks the microphone. /api/agent-session returns a signed URL and her agent token.
  4. The agent says "Hi, I'm loading today's numbers" and calls get_briefing.
  5. The API returns the Andina briefing. The agent says: "October revenue in Andina fell 4.2%, mostly from online. Want to dig into that?"

Case 3: she asks for a new measure within the use case

She asks: "What share of our revenue was online, week by week, for the last eight weeks?"

  1. The agent says "Let me pull that" and calls run_analysis with her words.
  2. Claude maps the question to sales_performance: derived metric share(revenue, channel = online), weekly grain, last 8 weeks. It classifies it as an extension, because it is built from catalog parts.
  3. The compiler validates the spec, adds region IN ('Andina') from her token and the date filter, and builds one SELECT.
  4. Athena runs it in a few seconds. The rows are stored as result_id = r_81f2.
  5. Claude writes a two-sentence summary from the rows, and its numbers are checked.
  6. The API returns the summary and r_81f2 to the agent. The agent reads the summary and calls render_chart(r_81f2).
  7. The page fetches GET /results/r_81f2 with her token and draws a weekly line chart.

The compiled SQL, simplified:

SELECT date_trunc('week', o.order_date) AS week,
       sum(CASE WHEN o.channel = 'online' THEN o.net_amount ELSE 0 END)
         / sum(o.net_amount) AS online_share
FROM gold.v_orders o
JOIN gold.v_stores s ON o.store_id = s.store_id
WHERE s.region IN ('Andina')                              -- from her token, always added
  AND o.order_date >= date_add('week', -8, current_date)   -- time filter, always added
GROUP BY 1
ORDER BY 1
LIMIT 50

Case 4: she asks for something outside the catalog

She asks: "How many customers did we lose this quarter?"

  1. The agent calls run_analysis.
  2. Claude finds no customer or churn data in the catalog. It returns out_of_scope with the reason "needs customer-level data, which is not in gold".
  3. Nothing runs in Athena. The question and the reason are logged for the backlog.
  4. The agent says: "I don't have customer-level data, so I can't measure churn. The closest I can show is weekly order counts. Want that?"

12Operations

Observability

  • Log every analysis as one structured record: question, spec, scope class, SQL hash, bytes scanned, Athena time, total time, user and refresh version.
  • Trace the voice path end to end, from tool call to Athena, with X-Ray or OpenTelemetry.
  • Use ElevenLabs conversation analytics to find failed tool calls and sessions that drop off.

Cost drivers

ComponentDriven byControl
AthenaData scanned per refresh and per on-demand questionPartitioning, compaction, result reuse, per-query scan limit
Bedrock (Claude)One briefing per partition per refresh, plus two calls per questionSend only the matching catalog entries; cache repeated specs
ElevenLabsConversation minutesSession timeout, short agent replies
Serving (S3, Lambda, API Gateway)RequestsSmall at dashboard scale

Testing

  • Golden questions: 50 to 100 questions, each with its expected spec and scope class. Run them on every catalog or prompt change, and fail the build if accuracy drops.
  • SQL snapshots: each golden spec must compile to its expected SQL.
  • Briefing checker: feed it briefings with planted wrong numbers; it must reject every one.
  • Access: a token for one region must never return another region's rows.

Governance loop (weekly)

  • Derived metrics that users ask for repeatedly are reviewed and promoted into the catalog, with a name and a description.
  • Out-of-scope requests go to the product backlog. A cluster of similar requests is a candidate new use case.
  • Catalog changes go through pull requests and ship together with the gold views they depend on.

13Build order and open decisions

Build one use case end to end first, then add use cases to the catalog.

  1. Lake ingest to gold for one use case, ending in the gold.refreshed event.
  2. Metric catalog and compiler for that use case, with the golden-question tests.
  3. Refresh pipeline: snapshots, Claude briefing and checker.
  4. Analytics API with the JWT authorizer and row filters.
  5. Next.js dashboard reading snapshots, with the D3 chart components.
  6. ElevenLabs agent with get_briefing first, then run_analysis and the client tools.
  7. Observability, cost limits and the governance loop. Then the next use case.
