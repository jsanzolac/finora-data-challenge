# Round 3: CDO final rules

I settle all 19 open disagreements (D1–D19) and leave none unresolved. The final set has **61 rules: bronze 11, silver quality 15, silver business 17, gold 18. 51 are keep and 10 are flag.** 19 rules are dropped or merged.

Changes from the ETL_FINDINGS.md §2 draft:
- **No NULL amount ever reaches silver.** A malformed amount, month or ID, a duplicate key or a missing customer-month now rejects the file (D1), and CRO-01 merges into SQ-08. A file reject holds back only its own dataset, and each dataset has its own watermark (D2).
- **`sm_spend_per_new_logo` moves to its own gold view.** It leaves `agg_month_kpis` and becomes a separate view under the reinstated ID CMO-05 (D11).
- **Revenue logic is pinned down.** Retention headlines use point-in-time `amount_normalized` (D6), the settlement tests run in a fixed order (D5), and churn counts after `as_of_month` − 2 are NULL (D18).
- **Bronze adopts the CTO's security texts** (D12–D14), and CDO-11 now protects money, not counts (D3).
- **Re-checked.** I re-checked every disputed figure over `data/` with `python3 -I` and `Decimal`, plus read-only S3 calls (2026-11-15). 44 rules changed in substance and are marked "(changed in R3)".

## onFailure and status semantics

| Action | What happens | Where it goes | Downstream |
|---|---|---|---|
| reject (file) | The file is not accepted. A reject record holds the rule id, the reason and the offending line numbers. Data and the dataset owner are alerted | `_rejected/<dataset>/` with its manifest; readable by Data | That dataset stays at its previous accepted snapshot. The other datasets still advance, and the previous published run stays live |
| reject (run / export) | The run, or the export, fails as a whole | The run or export report | Nothing new is published. The previous published run stays live |
| quarantine (row) | The row is held out of silver with its rule id and reason, and it is counted in the reconciliation | Silver `_quarantine/`; readable by Data | The rest of the file continues |
| quarantine (file) | The pipeline does not read the file. It is released only by a recorded override (approver, reason). Quarantined bytes are never edited | Bronze `_quarantine/` with its manifest. Readable only by the security role, plus the CDO for a schema change | That dataset stays at its previous accepted snapshot. The other datasets still advance |
| flag | The data passes unchanged. The hit is recorded in a flag or reason column (silver, gold) or in the manifest (bronze), and it is counted in the run report. "Alerts" means it also notifies the named team. A KPI set to NULL by a rule is a flagged value inside an atomic publish, not a partial publish | In place | Continues |

- **Gold object rules:** onFailure applies when the built object breaks its stated grain, keys or contents.
- **Inferred = true:** the rule asserts a meaning or expectation that no owner has stated, so it comes from the data.
- **Inferred = false:** the rule implements an owner definition (SB-01, SB-02) or is a control. Controls cover security, format, reconciliation, lineage, access and publishing, plus status columns that record that an owner has not answered.
- An inferred rule stays marked until the owner's statement is recorded verbatim in `owner_definitions.md`.

**Status:**
- **keep:** final. Build it as written.
- **flag:** final, and built as written now, but a named owner answer (Q#) is expected to change its text, parameters or onFailure. It is revisited when that answer is recorded.
- An owner answer that only replaces a value in versioned config (factors, mappings, currency, basis or scope statuses) does not by itself make a rule flag.
- **(changed in R3):** the meaning, onFailure or scope differs from the §2 draft. Merging §2's quoted fragments into one text without changing their meaning is not marked.

## Notes for the CTO

- **One versioned config file,** hashed into `_rules_version`. It holds:
  - the owner factors (10,000 and 100,000,000, citing `owner_definitions.md`);
  - the registry: keys, headers and scales;
  - the size ceilings and the industry domain with its codes;
  - the spend seed: `spend_group`, `channel_class` and `is_hr_sensitive`;
  - the rule parameters:

    | Parameter | Value |
    |---|---|
    | Settlement tolerance | 0.05 |
    | Censoring multiples | {2, 3} |
    | Churn threshold | 3 months |
    | Outlier ratio and minimum payments | 25 and 3, plus the owner overrides |
    | Tripwire bounds | [0.5, 20] |
    | Suppression threshold | 5 |
    | `low_n` threshold | 10 |
    | `sm_regime` boundary | 2023-06 |

  - the status values for currency, basis and scope.

  An owner answer means changing this file and running a rebuild.
- **Order of evaluation:**
  - **Bronze:** BRZ-05 → BRZ-03 → CTO-02 checksum → BRZ-02 → CDO-01 → CDO-02 → BRZ-04 → BRZ-01 → write (BRZ-06, CTO-03) → CTO-01 → manifest.
  - **Silver, file-level, per dataset:** SQ-01 → SQ-02 → SQ-03 / SQ-05 / SQ-06 / SQ-07 / SQ-09 / SQ-10 → CDO-05 → SQ-08 → CDO-06. A snapshot is "accepted" only after all of them pass.
  - **Silver, then:** SB-01/02 → SQ-04 / SQ-12 → SB-03 → SB-04 → SB-06 → SB-05 / SB-07 / CDO-07 → CRO-03 → CRO-05 → SB-08 → CRO-07 → SB-10 → SQ-13 / CDO-08 / CTO-07.
  - **Gold and publish:** CDO-04 (silver leg) → gold → CDO-04 (gold leg), CTO-08, the CDO-10 CI test → atomic publish.
- **Arithmetic:** every comparison and every tolerance is computed in Decimal. The SB-08 portfolio median uses all positive customer-months up to `as_of_month`. `as_of_month` is `revenue_complete_through`, so `is_provisional` and `churn_confirmed_through` move with it.
- **No `amount_status` column:** no NULL amount can reach silver. A KPI NULLed by a rule is a value inside an atomic publish, not a partial publish.
- **Access by area:**
  - row quarantine: readable by Data;
  - file quarantine: the security role only, plus the CDO for CDO-02;
  - `_rejected/`: readable by Data.
- **Lineage when a row has two sources** (for example `dim_customer` from Transactions and Industry): it must still trace to both SHA-256s, either through per-source columns or through the run manifest. Your choice.
- **Re-delivering identical bytes** (A, B, A): no new bronze object is written, but A becomes current again (CTO-03).
- **CI lints:**
  - no gold column named `cac`, `payback`, `ltv`, `mrr` or `arr`;
  - no spend join outside `dim_month` and `dim_spend_category` (CDO-10);
  - exports come only from gold (CTO-09).
- **CDO-11:** use IAM for the named roles now. Build the suppressed share views before the first grant to any other role.
- **Bronze rename, my recommendation:** name bronze objects by dataset id (`sm_spend/…/sm_spend__<ts>__<sha8>.csv`, as your layout already does), and keep `s_and_m/S&M_spend.csv` verbatim as the manifest's source key.
  - It does not break the bronze contract. The contract governs columns and values, which CTO-01 proves are unchanged byte for byte, whereas a `_source_file` column would be a forbidden second column.
  - It removes the `&` that S3 events encode as `%26`.
  - **The user makes the final call.** If the name is kept, BRZ-05 still forbids interpolating the key anywhere.
